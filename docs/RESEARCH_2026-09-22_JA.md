## 2. 設計の前提で訂正すべき点

### 2.1 confidence は操作成功率ではない

TypeSafeの `confidence` は、Choice/Scoreが返す確率分布の偏りをまとめた統計量である。「0.95なら95%の確率で正しく操作できる」という意味ではない。`probabilities`、候補の適切さ、観測の鮮度、実操作の結果を別に扱う。アプリごとの固定閾値だけで安全性を決めない。

参考：[公式 Confidence](https://docs.typesafe.ai/confidence)。

### 2.2 同時質問は、前の回答を読んでから次を考える処理ではない

公式文書は、同一リクエスト内の質問が互いの回答を隠れた文脈として使わないことを明記している。現在の `target`、`action`、`risk` は同時に聞かれているため、`risk` が「実際に選ばれた対象・実際の入力内容を確認した結果」になっているとは保証できない。

提案は、**操作種類・対象・用意済み引数を1つの具体的な操作候補に結び付けること**。たとえば `A17 = このウィンドウの保存ボタンをクリック` とする。危険度をモデルに追加判断させるなら、各候補を名指しした質問を並列に作るか、選択後の具体的な操作を次の呼び出しで検査する。関係のない回答はコード側で使わない。

これは「全部の質問を別々に呼べ」という意味ではない。同じ観測で答えられる状態判断や候補別の検査はまとめられる。

参考：[公式 Primitives](https://docs.typesafe.ai/primitives)、[Fan-out](https://docs.typesafe.ai/patterns/fan-out)、[現行質問生成](https://github.com/Sac-Y/Jev-cu/blob/e2cc92d731fac6e6aeb7acbd3c105cf23552cdec/scripts/jev-decide.mjs)。

### 2.3 選択式でも、画面内の誘導文に影響され得る

Jev 1.13の公式の制限には、悪意ある指示や誘導を含む入力によって回答が変わり得ることが記載されている。「文章を生成しない」「選択肢しか返せない」ことは、危険な選択肢を選ばない保証ではない。許可や操作範囲はモデルの外で管理する。

短いIDは機械用の識別子として使う。ただし、意味の説明まで削って難しい符号辞書を解かせる設計は避ける。数値計算、経過時間、厳密な件数はコードで処理する。

参考：[Jev 1.13の既知の制限](https://docs.typesafe.ai/model-jaggedness/jev-1.13)（文書内の確認日2026-09-17）。

### 2.4 二重のモデル判断は、独立した成功証拠ではない

Jevが `done` を選び、別のNoulでも目標達成らしいと答えても、同じ不十分な観測を使っていれば一緒に誤る可能性がある。`DONE_PROPOSED` と `DONE_VERIFIED` を分ける。後者には「何を確認したか」「どの観測を根拠にしたか」が必要。

ボタンの存在、クリック命令の終了、画面の変化だけで保存・送信・生成の成功とはしない。GUIテストでは、必要に応じて再表示・再読込などのユーザー経路で確認する。評価用の内部検査を併用する場合は、操作側が見た情報と評価側だけの正解情報を分離して記録する。

参考：[Jev Browserの質問](https://github.com/jkudish/jev-browser/blob/f731c7aa773f55a30dad7175bbb358b2d8529e57/src/questions.ts)、[Ottoの検証契約](https://github.com/NobleSpartan6/otto/blob/main/docs/agent-bridge.md)。

## 5. Astra＋JevのMinecraftから得られること

### 5.1 最新の経路と、できたことの範囲

主に確認したのは [rmalde/minecraft-agent](https://github.com/rmalde/minecraft-agent)、現在の `nether-agent.mjs`、`async-planner.mjs`、`end-combat.mjs`、`optimization/nether/REVIEW.md`。旧 `agent.mjs` だけで最新の挙動を代表させない。

READMEの最新報告は `nether-final-08`、8分43秒台、Jev 131回・Astra 35回・ベッド攻撃6回・死亡0回。ただしこれは、事前調査された固定シード、Survival/Peaceful、既知の物資・経路、自然に有効なEndポータルなどを利用した条件である。生ログや録画をこちらが再実行・独立検証したものではない。

**画面だけを見て人間と同じキー操作をした実験ではない。** 構造化されたゲーム状態、Mineflayer、経路探索、ゲーム固有の衝突・在庫・センサー情報を使う。Windowsの任意アプリを同じ精度で操作できる証拠にはならない。参照：[README](https://github.com/rmalde/minecraft-agent/blob/main/README.md)。

### 5.2 Jevの選択肢は「1キー」より大きい

現在の経路では、準備中は物資回収・必要なクラフト・ベッド回収・出発、移動中は短い接近・ポータル操作・橋の1ブロック配置、戦闘中は退避・遮蔽物への移動・ベッド攻撃・待機など、段階に応じた操作を提示する。

特に `one_timed_bed` は、1つの選択に対してベッドの準備、狙い、最大16秒の条件待ち、条件が成立した時だけ1回攻撃する処理を持つ。近くにブレスが来る、遮蔽物の位置を失う、ベッドが消える等で中断する。したがって、**131判断＝131クリックではない**。

GUIへ応用するなら「同じ入力欄へ用意済みの値を入れて読戻す」のような、条件と終了確認の明確な短い操作単位が候補になる。一方、勝手に購入・送信までまとめたり、未知のダイアログを越えて実行したりしない。

参照：[nether-agent.mjs](https://github.com/rmalde/minecraft-agent/blob/main/nether-agent.mjs)、[end-combat.mjs](https://github.com/rmalde/minecraft-agent/blob/main/end-combat.mjs)。

### 5.3 古い計画を捨てる

`asyncPlanner` は初回計画の後、同時に複数の計画要求を走らせず、段階や時間に応じて更新する。計画の返答を待っている間にstageが変わった場合、その返答を捨てる。現在の既定間隔は15秒である。

この考え方は、Codexへ引き継いだ後に戻ってきた計画の扱いにも役立つ。ただしMinecraft側のstage一致だけを、GUIの同一対象・同一権限の保証へ転用してはいけない。GUIではファイル、ウィンドウ、ダイアログ、許可、タスク世代も確認する。

参照：[async-planner.mjs](https://github.com/rmalde/minecraft-agent/blob/main/async-planner.mjs)。

### 5.4 成功より参考になる失敗記録

以下は作者の開発記録であり、こちらの実機再現ではない。`nether-practice-*` や準備済み戦闘テストを、最終の連続成功と混ぜない。

|---|---|---|
| 村の遠い対象へ行けずタイムアウト | 接近を短い区間へ分割 | 長い操作単位を無理に再実行せず、中間の到達状態を確認 |
| ツルハシが在庫一覧から消えたように見える | カーソルに保持中のアイテム補正が未処理だった | 観測が欠けた場合を、実データ消失と即断しない |
| 到着点は安全なのに帰路で死亡 | ブレスの検査が目的地だけだった。経路・実行中の危険検査を追加 | 最後のボタンだけでなく、途中のダイアログ・フォーカス変更も監視 |
| 家の壁越しに壊したベッドを拾えない | 回収に必要な時間よりタイムアウトが短い。接近後に壊し、落ちた物を優先回収 | 無変化を一律に失敗としない。何を待っているかと時間予算を持つ |
| 必要な行動があるのに待機 | 有用な候補のフィルターを別経路にも適用 | 待機を無条件で出さない。ただしGUIの処理中は待機が必要なため、その条件を定義 |
| 試験開始時に浮遊扱いで切断 | テスト用の足場チャンクが未読込 | 試験環境の準備失敗とモデルの判断失敗を別分類 |

### 5.5 移植前に見るべき懸念もある

[MinecraftのPR #2](https://github.com/rmalde/minecraft-agent/pull/2) は、個人のJavaパスやGoogleプロジェクトに依存する設定、ローカルrelayの認証、録画アップロード、依存関係、テストの実行範囲を改善する提案で、今回の取得時点では未マージだった。本文の多数のテスト成功も、修正版での完全なゲーム実行を確認したものではない。

設計の参考になることと、そのリポジトリをそのまま安全に実行できることは別である。今回、MinecraftのソースはこのForkへ直接移植していない。

[Issue #1](https://github.com/rmalde/minecraft-agent/issues/1) にはJevを介する必要性への批判があるが、取得時点では本文・追加コメント・比較実験の根拠は付いていなかった。批判を事実認定には使わず、「同じ課題をCodexだけ／コードだけ／Jev併用で比較する必要がある」という評価項目に反映する。

## 6. 他の関連実装からの発見

### 6.1 ellistev/typesafe-minecraft-demo

[README](https://github.com/ellistev/typesafe-minecraft-demo/blob/main/README.md) は、旧来の高レベル操作と、250msの移動・30度の回転・狙い・装備・1ブロック操作を個別に選ぶ新しい方式を区別している。過去の131判断の映像を、新しい低レベル方式の実績として扱っていない。

失敗記録には、正規化したベクトルを誤って変更し視線判定の長さが1.05ブロックになったこと、目線の高さと視線判定の始点が違ったこと、左右の符号が逆だったことがある。候補を行き来する症状の原因が、Jevではなく観測・幾何処理だった例である。

応答が遅すぎる／判断中にプレイヤーが動いた場合は、返答を記録しつつ実行しない。再観測・API障害・timeoutの再試行に共有上限を設けている。GUIでも画面が変わった時の破棄と、モデル・通信・観測・操作の失敗原因の分離が必要。

### 6.2 Hermes and Jev play Minecraft

[README](https://github.com/teknium1/hermes-and-jev-play-minecraft) では、土の必要数を満たしても採掘を選び続けた、移動すべき時に待機を5回選んだ、という失敗を残している。対策は長い説得文ではなく、達成済みの採掘や不要な待機を候補から外すことだった。

参考にするのは「観測→候補→選択→実行」の境界であり、候補一覧を作っただけで外部からの実行要求も安全になるとはみなさない。実行側でも提示済み候補・引数・許可を検証する必要がある。同リポジトリのLinux再現報告も、こちらが再実行した実績ではない。

### 6.3 Jev Browser

[質問とループ](https://github.com/jkudish/jev-browser/blob/f731c7aa773f55a30dad7175bbb358b2d8529e57/src/questions.ts) の行動・goal・stuckの分離は参考になる。ただし `goal_achieved` という名前の状態もモデル判断から到達できるため、名称だけで検証済み成功としない。

[変更履歴](https://github.com/jkudish/jev-browser/blob/f731c7aa773f55a30dad7175bbb358b2d8529e57/CHANGELOG.md) には次の失敗への対応がある。

- 入力欄のlabel解決が不十分で、入力欄が候補に出なかった。
- 入力は成功したのに「画面変化なし」と記録され、stuck扱いになった。
- 文字入力にEnterを混ぜていたため、複数欄の途中でフォームを送信してしまう設計だった。入力と送信を分離した。
- 生成モデルの空出力や失敗を、適当な単語列の入力で隠さないようにした。

このため、ループ検出は画面テキストの単純一致だけにせず、入力値・選択状態・保存状態など操作ごとの結果で判断する。比較用のログ文言を日本語化しただけで制御が変わらないよう、機械用コードと表示文も分ける。

### 6.4 Otto：Windowsの操作契約に近い参考例

[Otto](https://github.com/NobleSpartan6/otto) はmacOS/Windowsのnative操作を扱う初期alpha。今回の主題に近いが、任意アプリの互換性や日本語OCRが完成しているわけではない。READMEではOCRの同梱言語は英語とされている。

[agent bridge](https://github.com/NobleSpartan6/otto/blob/main/docs/agent-bridge.md) は、正確なアプリ範囲、期限付きの観測参照、1～16手の既知操作、Jevへの限定委任、操作数と検証結果の区別、同一デスクトップ上の実行競合を扱う。

**`run_steps` はモデルを呼ばない既知手順の実行。`delegate` はJevが許可済み候補から選ぶ処理。両者を混同しない。** 今回の案でも別モードにするのが自然である。

[Codex使用量の評価記録](https://github.com/NobleSpartan6/otto/blob/main/docs/evaluation-codex-agent-bridge.md) は、同じ6欄を埋める1組のmacOS試験で、MCP呼び出しが7回から1回になったと報告する。ただし両方式ともOtto内でモデルは呼んでおらず、Jevの効果測定ではない。キャッシュ・実行順・1回ずつという制限もある。

同記録は、承認条件の不一致で書き込み前に止まった失敗と、起動時警告を評価器がツールエラーと誤認した失敗を保持している。後者は元ログを消さず再採点している。試験コードの失敗を製品の失敗に混ぜず、失敗を削除して成功率だけ報告しない点が参考になる。

## 7. 提案する実装順序

### 第1段階：安全・診断の土台

Windows側では、実際のセッションが公開するAPI、対象ウィンドウ、取得できる情報、入力権限を読み取りだけで確認する。`cua`、`sky`、UIA、DOMがあると想定してコードを決め打ちしない。候補0件を「対象がない」「観測非対応」「読込中」「認証で見えない」に分ける。非対応を保護設定の解除で回避しない。

同時に、API送信先固定とリダイレクト拒否、本文までのtimeout、応答サイズ・型・数値範囲の検査、すべてのログ出口の機密保護を実装する。モデルの明示バージョンとschema/Policyの版を記録し、検証中に無意識に条件を変えない。

### 第2段階：選択した操作を、そのまま安全に実行する契約

概念例：

```text
操作ID A17
  対象ウィンドウと要素の参照
  操作種類と準備済み引数
  観測ID・期限・前提状態
  許可された影響範囲
  検証する結果
```

JevはIDを選ぶ。実行側は、同じ操作レコードと新しい観測で再検証してからdispatchする。`resources.at`などで選択後に実体を差し替えない。候補外・期限切れ・引数不足は実行しない。`NONE`、再観測、Codexへの返却を成功扱いにしない。

実行前の再確認は重要操作だけに限定せず、基礎的な対象・状態確認を全操作で行う。危険操作には追加の影響確認と、必要な具体的許可を要求する。JevのSAFEは許可を増やさない。意味付き要素が取れない座標操作は、別の検証条件を持つまで無効にする。

### 第3段階：結果・停止・再開を整理する

```text
処理先：EXECUTE / REOBSERVE / REASONING / VISION / ASK_USER / VERIFY_GOAL
操作結果：EXPECTED / PARTIAL / NO_CHANGE / WRONG / UNKNOWN / ERROR
全体結果：DONE_VERIFIED / NEEDS_HANDOFF / BLOCKED / CANCELLED
終了理由：AUTH / INFO / RISK / LOOP / MAX_STEPS / TIMEOUT / TECH_ERROR など
```

これは提案であり、既存APIの実装済みenumではない。`BLOCKED` は「現在の権限・情報・機能・予算では進めない」であって、あらゆる方法で解決不能と断定する状態ではない。

技術エラーや経過時間はコードで確定する。モデル由来の状態は推定として残す。`DONE_VERIFIED`には確認条件と観測根拠を付ける。途中まで成功していればその範囲を保存し、同じ操作を再送しない。操作送出済みで結果不明なら `uncertainAction` を返し、観測せず自動再実行しない。

再観測・待機・API再試行・Codexへの引き継ぎにも、実行全体の共有予算を適用する。再呼出しで上限を無制限にリセットしない。遅れて届いた計画・判断はタスク世代と状態を確認してから使う。同一デスクトップへの自分たちの並行操作は排他し、人間の介入や別ツールによる変更も鮮度検査で扱う。

### 第4段階：小さな実機試験と比較

最初は使い捨ての電卓・入力用アプリで、観測のみ→dry-run→1手の実操作→短い複数手、と段階的に進める。上限16手などの数字を最初から安全性の根拠にしない。

比較は、同じ開始状態と成功条件で「Codexが逐次判断」「既知手順のコード実行」「Jevに限定委任」を分ける。観測・候補生成に毎回大型LLMが必要なら、Jev追加で速くなるとは限らない。

記録するのは、独立確認した目標達成、誤操作・誤完了・誤った自己処理、正しい／過剰な引き継ぎ、再試行、介入、実時間、全モデルの呼び出し・利用量。単体テストの成功、静的候補選択、ライブAPI、実GUI、途中修正付き再開、無介入の連続実行を区別する。信頼度だけを上げる調整ではなく、既知の正解・不正解・判断不能例に対する実際の結果を測る。

## 8. 次の実装へ渡す結論

現在までの役割分担と、再観測・Codexへの引き継ぎ・停止理由の分離は維持してよい。大きな修正点は次の三つである。

1. 個別に選んだ対象・操作・引数を後でつなぎ合わせず、具体的な許可済み操作を一つの単位として選ばせる。
2. Jevを安全性や完了の最終権限にしない。観測、許可、モデル推定、実行、結果証拠を分ける。
3. Minecraftの設計を参考にしつつ、固定シード・内部状態・手作りの操作関数による利点を、汎用Windows操作の性能として持ち込まない。

実装前に必要な外部情報は、Windows実機で現在利用できるComputer Useの観測・操作APIと、その画面情報の形式である。それ以外の通信保護、操作契約、状態遷移、模擬テストは、このFork上で先に設計・実装・検証できる。
